# osi 产品说明（面向产品经理）

## 一句话介绍

`osi` 帮助团队在评审一项进行中的 OpenSpec 需求时，快速找到仓库里可能相关的代码入口、历史上常一起修改的文件，以及仍需人工确认的风险。它提供可追溯的线索，不替产品或研发决定改动范围。

## 它解决什么问题

需求通常写在变更说明里，代码却分散在页面、服务、配置和测试中。评审者需要把需求里的业务描述对应到代码入口，再检查相关能力是否共用、历史上是否联动修改。完全靠记忆和手工搜索，容易遗漏旧入口，也很难说明判断依据。

`osi` 从进行中的 OpenSpec 变更文档提取明确的代码引用，在项目里检索这些引用，再用 Git 历史补充曾一起修改的文件。结果保留了“为什么找到这个文件”的线索，方便产品经理与研发一起核对。

## 适用场景

- 需求评审：在确定方案前，找出值得研发确认的代码入口和关联模块。
- 影响面复核：实现过程中或完成后，结合实际变更检查需求覆盖和遗漏风险。
- 交接与讨论：用文件路径和证据类型展开讨论，减少只凭模块名称猜影响面的情况。

它适用于使用 OpenSpec 管理需求变更、且本地能访问代码仓库的团队。主要使用者可以是产品经理、技术负责人和开发者；产品经理通常阅读生成的影响面报告，与研发共同做最终判断。

## 工作方式

```text
OpenSpec 变更文档
        ↓ 提取明确引用（路径、类型名、API、权限码等）
项目代码搜索
        ↓ 找到候选文件，并保留命中理由
Git 同改记录 + 少量同目录线索
        ↓
影响证据（YAML） → 可选的影响面报告
```

默认只使用文档中明确标记的代码引用，不会把标题或普通描述词当成代码搜索词。标记为“不在范围”等内容里的引用不会用于搜索。`osi` 不调用大模型来选择文件；命令行结果来自规则化的文本匹配和 Git 记录。

## 怎么使用

主要命令是：

```bash
osi impact <变更 id 或路径>
```

例如：

```bash
osi impact add-renewal-status
```

项目需要有进行中的 `openspec/changes/<变更>/`，环境需要 Node.js 18+ 和 Git，且 `osi` 已安装到命令行路径中。变更也可以用目录路径指定。

命令输出 YAML 证据。若团队使用 Cursor、Claude Code、Codex、Windsurf、Cline、Roo Code、OpenCode、GitHub Copilot 或 Pi，可以先在目标 OpenSpec 项目执行 `osi init`。它会报告检测到的项目配置，列出这些 agent，并预选检测到的项。上下键移动，空格勾选或取消，回车安装；没有检测到时不预选，仍可以手选。脚本使用 `osi init --agent cursor,claude`。安装后在多数工具里运行：

```text
/opsx-impact add-renewal-status
```

Codex 的调用是 `$opsx-impact`。技能会结合变更文档、证据和适用时的代码差异，生成中文或当前对话语言的报告，分为“一句话、影响范围、可能遗漏、故意没动、上线注意”。报告以对话形式呈现，不写回变更目录。

## 如何读结果

`osi impact` 包含四类主要信息：

| 字段      | 面向产品评审的解释                                                                                                          |
| --------- | --------------------------------------------------------------------------------------------------------------------------- |
| `seeds`   | 与变更中的明确引用命名对应、并达到高置信条件的代码文件。它们是后续核对的起点，不是完整改动清单。                            |
| `refs`    | 每个 seed 的引用词、其它文件中的同词出现数量及最多 8 个示例路径。它说明名称出现在哪里，不证明这些文件调用了 seed 或依赖它。 |
| `history` | 与 seed 有合格 Git 同改记录的文件，或在特定条件下补充的少量同目录兄弟文件。它是历史关联线索，不是修改要求。                 |
| `change`  | 本次变更的名称和文档路径，便于确认分析对象。                                                                                |

常见 history 行包含 `path`（相关文件）、`via`（由哪个 seed 带出）、`reason`（线索类型）和 `commits`（同改次数）。`reason: co_change` 表示历史提交中曾与 seed 一起修改；`reason: sibling` 表示没有合格同改记录时，按有限的同目录文件名或引用样例补出的线索，`commits: 0` 不代表历史支持。

`refs.others` 是同一引用词出现在其它源码文件中的数量，不是依赖数量，也不是风险分数。词项过于常见时会标记 `wide: true`。为避免把大量无关文件扩散到结果中，`refs.others` 达到 30 的 seed 不继续展开 history；超过 80 个文件的宽词命中也不会作为普通内容候选扩散。高复用词因此可能带来较少的关联线索，评审时需要回到需求和模块知识做判断。

## 证据边界

- 文件被列出表示它匹配了明确引用或满足限定的历史规则，不表示它一定需要修改。
- 同改次数是过去的共同变更频次，不是影响置信度、重要性或发布优先级。
- `sample` 表示引用词也出现在这些路径中；它不代表导入关系、调用关系或实际依赖。
- `osi` 不分析 AST、依赖图或 Git blame，也不理解业务语义；没有被明确引用、名称不匹配或历史不足的代码可能不会出现。
- 搜索只覆盖项目中的可搜索源码类文件；OpenSpec 文档、Markdown 文档、依赖、构建产物等不会作为候选。
- `history` 主要基于近 18 个月内的非合并提交；忽略一次改动超过 30 个文件的提交，同一文件对至少共同出现 2 次才构成同改线索。每个 seed 最多输出 10 条，总量最多 50 条。
- 候选、seed 和 history 受规则及数量上限影响；空结果表示没有找到符合规则的证据，不等于没有影响。

## 相关命令

| 命令                 | 作用                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| `osi impact <变更>`  | 默认工作流，输出 seed、引用频次和历史关联证据。                                                |
| `osi scope <变更>`   | 只看从变更引用检索到的概念、候选文件和测试文件，可用于定位搜索结果。                           |
| `osi history <变更>` | 只看 seed 与历史/同目录关联，不输出 `refs`。                                                   |
| `osi init`           | 在 OpenSpec 项目安装所选 agent 的 opsx-impact 技能。交互时预选检测到的配置；脚本用 `--agent`。 |

`--no-search` 可跳过仓库搜索；`--include-low` 可在 `scope` / `impact` 中增加低置信度候选。完整命令和 YAML 结构见项目根目录的 README。

## 产品使用建议

把 `osi impact` 当作评审准备和遗漏检查的证据入口：先确认 OpenSpec 变更文档里的路径、类型、API 和权限码写得具体；再让研发核对 seed 与 history，结合业务流程、代码差异和测试判断最终范围。对高复用词、空结果、`sibling` 线索和没有 Git 历史的仓库，尤其应以人工核对为准。
